# 1. Teacher 不需要把整个后续任务做完

现在假设：

```text
OFT 抓失败
   ↓
Teacher 回撤
   ↓
重新对齐
   ↓
重新抓住书
   ↓
抬升
   ↓
移动到篮子
   ↓
放置
```

如果 **重新抓住以后 OFT 本身已经能够继续任务**，那 teacher 继续负责：

> 抬升 → 搬运 → 放置

实际上是在让 recovery policy 学 OFT 本来就会的能力。

更合理应该是：

```text
OFT
 │
 ▼
failure
 │
 ▼
Recovery Policy
 │
 ├─ retract
 ├─ re-align
 └─ re-grasp
 │
 ▼
进入 OFT 可恢复执行的状态
 │
 ▼
handoff
 │
 ▼
Frozen OFT
 │
 ├─ lift
 ├─ transport
 └─ place
```

也就是：

[
\boxed{
x_f
\xrightarrow{\pi_R}
x_{\text{handoff}}
\xrightarrow{\pi_{\text{OFT}}}
\text{task success}
}
]

其中：

* (x_f)：failure state；
* (\pi_R)：recovery policy；
* (x_{\text{handoff}})：OFT 可以重新正常工作的状态；
* (\pi_{\text{OFT}})：冻结的 nominal policy。

这其实和 RecoveryChaining 的定义很接近：recovery policy 的目标就是回到 nominal controller 能重新接管的状态，而不是自己完成余下整个任务。([arXiv][1])

### 这对我们之前的 4/5/6 三个问题都有帮助

尤其是问题 6。

原来 teacher trajectory：

```text
关键 fork
↓
重新对齐
↓
抓取
↓
抬升
↓
运输
↓
微调
↓
放置
↓
后期大量普通动作
```

L1 中真正关键的 fork 只占很小比例。

现在缩成：

```text
关键 fork
↓
重新对齐
↓
重新抓住
↓
HANDOFF
```

那么关键 recovery 动作在 loss 中占比明显提高。

所以：

[
\boxed{\text{缩短 recovery horizon 会缓解问题 6}}
]

而且 recovery rollout 更短，也会减少连续误差累计，因此**也缓解问题 4 的 closed-loop compounding error**。

但注意：

[
\boxed{\text{它不能解决问题 5 的 multimodality}}
]

比如第一步本身：

```text
左绕 → 成功

右绕 → 也成功
```

这个 fork 依然存在。

# 2. 那怎么定义什么时候 handoff？

这个不能拍脑袋定成：

> “抓住就交回。”

更严格的定义应该是：

\$$
\boxed{
x_t\in\mathcal S_{\text{resume}}
}
\$$

其中：

* (x_t)：当前机器人/环境状态；
* (\mathcal S_{\text{resume}})：Frozen OFT 的 **resumable state set**。

最简单可以在仿真中验证：

从 recovery 中间状态 (x_t)：

```text
restore state x_t
       ↓
直接交给 OFT
       ↓
rollout
```

如果 OFT 后续成功率足够高：

[
P(\text{success}\mid x_t,\pi_{\text{OFT}})>\eta
]

就把这里定义为 handoff point。

其中：

* (\eta)：例如设定的可靠性阈值。

第一版甚至不用学一个 handoff network。

**离线找 teacher trajectory 上最早的 OFT-resumable state 就行。**

这会显著减少 recovery dataset 中大量实际上属于 normal manipulation 的动作。

# 3. 你觉得 Relation 没什么作用——这个担心非常重要

我也不会默认 Relation 一定有效。

目前最大的风险确实是：

[
\boxed{
H_t^a\text{ 本身可能已经包含足够的几何信息}
}
]

那么我们再加：

[
Slot\rightarrow3D\rightarrow Relation
]

最后效果可能很小。

如果这样，Relation 就只是“看起来可解释”，并没有真正提供额外 information。

所以必须问：

> **Relation 到底给 OFT 增加了什么它原来难以提取的信息？**

我认为唯一站得住的答案是：

[
\boxed{\text{显式、robot-frame、task-relevant geometric state}}
]

例如：

[
\Delta p^{g,ketchup}
====================

[-0.042,0.018,-0.031]\text{ m}
]

这种信息直接意味着：

> ketchup 相对 gripper 左 4.2 cm、前 1.8 cm、下 3.1 cm。

相比 dense visual latent，它是一个非常强的 corrective-control inductive bias。

# 4. Relation 会不会需要大量数据才能学？

**如果我们让 Relation 本身完全靠网络“悟”，会。**

例如：

[
r^{ij}
======

MLP(z_i,z_j)
]

只有几百条 recovery trajectory，我对此并不乐观。

所以我现在反而建议 Relation Encoder **尽量少学东西**。

例如直接构造物理 relation vector：

[
\boxed{
q_t^{g,i}
=========

[
\Delta x,
\Delta y,
\Delta z,
d,
z_t^i
]
}
]

其中：

* (\Delta x,\Delta y,\Delta z)：object 相对 gripper 的 robot-frame offset；
* (d)：Euclidean distance；
* (z_t^i)：object semantic slot。

然后只做一个线性投影：

[
\boxed{
r_t^{g,i}=W_rq_t^{g,i}+b_r
}
]

其中：

* (W_r,b_r)：可训练 projection。

也就是说：

> **几何关系不让网络学，几何关系直接算出来；网络只学怎样使用它。**

这样对数据量要求会低很多。

我现在其实更喜欢这一版，而不是一个复杂 Relation MLP。

# 6. Slot tracking 是否需要？我现在的答案是：**需要，但不是 SlotSSM**

这个区别很重要。

我们不需要：

[
\text{Slot temporal dynamics memory}
]

但需要：

[
\boxed{\text{Slot identity consistency}}
]

因为假设连续两帧：

```text
t:
slot 1 = ketchup
slot 2 = basket

t+1:
slot 1 = basket
slot 2 = ketchup
```

那 relation tokens 会疯狂跳变。

所以：

[
r_t^{g,1}
]

和：

[
r_{t+1}^{g,1}
]

根本不是同一个对象。

这会影响：

* Gate 稳定；
* recovery action 稳定；
* task-conditioned relation retrieval。

# 7. SlotVLA 这里确实值得借

SlotVLA 明确做了 **temporal consistency**：利用 box/mask annotation 将跨帧相同实例对应起来，并设计 tracking loss；它还用 language 做 task-aware slot filtering，只保留少数任务相关对象。([arXiv][2])

我觉得我们可以借两样：

### A. Slot tracking supervision

让：

[
z_t^{ketchup}
\leftrightarrow
z_{t+1}^{ketchup}
]

保持 ID 一致。

### B. Task-aware filtering

原来：

[
K=10
]

经过 instruction：

> put ketchup into basket

过滤成：

```text
ketchup
basket
可能还有 gripper-relevant object
```

再构造 relation。

这样：

[
K^2
]

关系爆炸的问题也没了。

---

# 8. 但我不建议照搬 SlotVLA 的整个 temporal architecture

我们需要区分：

[
\boxed{\text{Tracking} \neq \text{Memory}}
]

Tracking 只是：

> ketchup 下一帧还是 ketchup。

我们不要求网络记：

> ketchup 五秒前发生了什么。

实际上今年已有工作指出，对于 object-centric video representation，部分时序一致性问题甚至可以通过显式 correspondence / Hungarian matching解决，而不一定需要复杂动态模型。([arXiv][3])

所以当前方法可以是：

[
\boxed{
\text{Slot Attention}
+
\text{Temporal ID Consistency}
}
]

而不是：

[
SlotSSM.
]

这很符合我们目前的 relation-recovery 故事。

# 9. 问题 4 和 5 能不能用 Diffusion Policy？

这个问题需要分开回答。

## 问题 5：多模态动作平均

### Diffusion 非常适合。

这正是 Diffusion Policy 的强项之一。

普通：

[
\hat A=f(C_t)
]

配 L1，很容易面对：

[
A_L,\quad A_R
]

学出中间。

Diffusion 学的是：

[
\boxed{
p(A_{t:t+H}\mid C_t)
}
]

即整个**动作轨迹分布**。

于是：

```text
        condition C_t
             │
       ┌─────┴─────┐
       ▼           ▼
left recovery   right recovery
 trajectory      trajectory
```

它可以 sample 某一个完整 mode，而不是回归平均轨迹。原始 Diffusion Policy 专门展示了同一状态下左/右两种有效轨迹都可以被建模，并且一次 rollout 会保持在一个 mode 中；它还强调 action-sequence diffusion 对多模态和时序一致性的优势。([arXiv][4])

所以对**问题 5**：

[
\boxed{\text{是，我认为 Diffusion 是一个很值得考虑的解决方案。}}
]

# 10. 而且特别适合我们的“短 Recovery Segment”

这个组合我反而越来越喜欢。

因为我们刚才决定 recovery 不做完整任务：

[
\text{failure}
\rightarrow
\text{re-establish grasp}
\rightarrow
\text{handoff}.
]

那么可以让 Diffusion Recovery Head 一次生成：

[
\boxed{
A_t^R=
[a_t,\ldots,a_{t+H_R}]
}
]

其中：

* (H_R)：较短 recovery horizon。

条件就是：

[
C_t
]

也就是 task-conditioned 3D relational context。

所以：

[
\boxed{
A_t^R
\sim
p_\theta(A^R\mid C_t,H_t^a)
}
]

比现在：

[
C_t\rightarrow\Delta H_t\rightarrow FrozenDecoder
]

其实还有一个潜在优势：

> **Diffusion recovery head 不受 frozen OFT decoder action manifold 限制。**

这是很重要的。

# 11. 这意味着甚至可以重新考虑 Recovery Adapter

现在有两条路线：

### 路线 A：Residual OFT

[
C_t
\rightarrow
\Delta H_t
\rightarrow
H_t^a+\Delta H_t
\rightarrow
D_{\mathrm{OFT}}
]

优点：

* 极简；
* 参数少；
* 很好讲 post-hoc correction。

缺点：

* frozen decoder 可能限制 recovery action；
* L1 action output 容易多模态平均。

---

### 路线 B：Relational Diffusion Recovery

正常：

[
A_t=A_t^{OFT}
]

失败：

[
\boxed{
A_t^R
\sim
D_\theta(C_t,H_t^a)
}
]

其中：

* (D_\theta)：小型 diffusion recovery action head；
* (\theta)：其训练参数。

也就是：

```text
             OFT
              │
           normal
              │
       ┌──────┴──────┐
       │             │
     normal         failure
       │             │
   OFT action    3D Relations
                     │
                     ▼
               Diffusion Head
                     │
                     ▼
              short recovery
                     │
                     ▼
                  handoff
                     │
                     ▼
                    OFT
```

这个其实非常干净。

# 12. Diffusion 能不能解决问题 4？

这里我要明确说：

[
\boxed{\text{不能彻底解决。}}
]

Diffusion Policy 使用 action sequences + receding-horizon control，可以每次重新观察、重新生成后续 action，因此会比一次性开环执行整段轨迹更有闭环纠错能力。([arXiv][4])

比如：

```text
预测 8 步
↓
只执行前 2~4 步
↓
重新观测
↓
重新 diffusion 8 步
```

这会显著减轻：

> 第一步稍微错了，后面 8 步还傻乎乎全部执行。

但：

[
\boxed{\text{Diffusion 仍然是在 offline demonstration distribution 上训练}}
]

如果机器人自己跑到了：

[
x_t^{policy}\notin D_{teacher},
]

Diffusion 也不自动知道那里正确动作是什么。

所以它**缓解 closed-loop error，不消灭 covariate shift**。

这是根据 Diffusion Policy 的 receding-horizon机制与 imitation learning 的分布偏移问题得出的判断；DAgger 的核心就是让训练数据覆盖 policy 自己诱导出的状态分布。([arXiv][4])

# 13. 所以问题 4 最靠谱的解决仍然是数据

例如：

### Round 0

teacher data：

[
D_0.
]

训练 recovery policy：

[
\pi_R^{(0)}.
]

### Round 1

让：

[
\pi_R^{(0)}
]

自己 rollout。

得到模型真正到达的：

[
x_t^{policy}.
]

然后 teacher 从这里给 correction：

[
(x_t^{policy},A_t^{teacher}).
]

加入：

[
D_1.
]

重新训练：

[
D=D_0\cup D_1.
]

这就是 DAgger-style data aggregation 的核心思想：让训练数据逐步覆盖 policy 自己实际访问的状态。([Proceedings of Machine Learning Research][5])

# 15. 我为什么开始觉得 Version B 可能更合理？

因为它同时解决了三个逻辑问题。

### ① Recovery 本来就是局部轨迹生成

不是另一个完整 VLA。

[
x_f\rightarrow x_{\text{resume}}
]

很适合短 horizon generative policy。

### ② FSM teacher 本身是 multimodal 的

Diffusion 天然比 L1 regression 更匹配：

[
p(A^R|C_t)
]

而不是强迫：

[
C_t\rightarrow\text{唯一 }A^R.
]

Diffusion Policy本身就是针对高维、多模态 action sequence distribution 设计的。([arXiv][4])

### ③ Normal 和 Recovery 职责彻底分开

正常：

[
\boxed{\text{Frozen OFT}}
]

failure：

[
\boxed{\text{Relation-conditioned short-horizon diffusion}}
]

恢复后：

[
\boxed{\text{return to OFT}}
]

“为什么不一直用 recovery policy？”也变得非常好回答：

> 因为 diffusion policy 的训练目标就是从 off-nominal states 回到 nominal policy 的 resumable set，而不是学习完整 task policy。

# 16. 但是它也有代价

我不会因为 Diffusion 很流行就盲目推荐。

最大问题有三个。

**第一，计算更慢。** Diffusion需要多次去噪推理；原始 Diffusion Policy 虽然可以实时运行，但本质仍有 iterative sampling cost，后续也出现大量工作专门做 one-step / flow acceleration。([arXiv][4])

**第二，模型复杂度比 Residual Adapter 高。**

你论文从：

> lightweight relational recovery adapter

变成：

> relational diffusion recovery policy。

这个故事会更重。

**第三，数据量要求可能更高。**

要学习：

[
p(A^R|C_t)
]

而不是一个局部 residual mapping。

如果你的 recovery trajectories 只有几十、几百条，我不会默认 diffusion 一定比简单 BC 好。
