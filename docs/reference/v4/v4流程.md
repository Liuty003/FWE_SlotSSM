# V4 自动恢复流水线

代码、数据、模型、评测与视频的长期保存位置统一登记在 [ARTIFACT_INDEX.md](./ARTIFACT_INDEX.md)。完整 LIBERO-Plus 10,030 条任务的新方法与公平输入协议见 [LIBERO_PLUS_10030_RECOVERY_METHOD.md](./LIBERO_PLUS_10030_RECOVERY_METHOD.md)。以后迁移到新任务时，也按该索引中的统一模板追加记录。

## 方法总览

我们最终做的是一套“冻结原策略 + 学习控制权 gate + 局部恢复策略 + 自动 DAgger 纠偏”的流水线。

整体逻辑：

原策略正常执行
↓
gate 连续检测到原策略失去能力
↓
恢复策略接管，执行局部纠偏
↓
gate 判断状态重新可由原策略完成
↓
归还原策略，继续完成长程任务

OpenVLA-OFT 7B 全程冻结。训练的只是约 55 MB 的 relation-3D、ownership gate 和 recovery action head。

## 一、构造初始数据

### 1. 跑原策略并挖掘失败

对同一任务族的全部 42 个任务运行 OpenVLA-OFT，保存轨迹、视频、动作与状态快照。

失败挖掘脚本：

scripts/mine_mug_pudding_failures.py

自动识别候选失败，例如：

- 空夹
- 抓错物体
- 过早闭合
- 接触但没有夹起
- 放置位置异常

人工视频审查只用于处理少量模糊案例，如 task557、548、564。

### 2. 从失败点恢复精确状态

根据失败时间和 MuJoCo snapshot 恢复精确环境状态：

scripts/restore_mug_pudding_failure_fork.py

这一步很重要：恢复 teacher 必须从原策略实际失败状态开始，而不是重新初始化一个近似场景。

### 3. 运行 privileged feedback teacher

从失败状态使用任务专用的 Cartesian teacher：

scripts/collect_mug_pudding_feedback_recovery.py

teacher 只负责局部恢复：

- 接近目标
- 对准并下降
- 闭合夹爪
- 抬升验证

成功条件不是“动作看起来合理”，而是：

- 与目标发生有效接触
- 目标附着于夹爪
- 目标抬升至少 3 cm

没有通过物理验证的 teacher 分支直接排除。

## 二、确定何时归还原策略

teacher 抬起物体后，不代表立刻适合归还 OpenVLA。

我们保存 teacher 每一步的 MuJoCo 状态，并从这些状态运行冻结 OFT，检查它是否能继续完成整个任务。

由此获得每个恢复轨迹的认证 handoff：

- handoff 前：RECOVERY
- handoff 边界：NORMAL
- handoff 后：由冻结 OFT 接管

最终 19 条成功 teacher 中有 18 条找到认证 handoff；task545 当时没有找到，但最终 learned recovery 在线测试仍成功。

数据整合：

scripts/build_ownership_dataset.py

生成：

- gate 状态数据
- recovery action 数据
- handoff manifest
- 数据质量报告

## 三、采集统一的 RGB-D 输入

旧轨迹只有 RGB，不足以训练 V4.3 relation-3D，因此重新采集了：

- 主视角 RGB
- 腕部 RGB
- 主视角 depth
- 腕部 depth
- 相机到机器人坐标系标定
- proprio
- 实例分割，仅用于训练监督
- OFT planned/executed action

采集器：

scripts/collect_v4_oft_rgbd_rollouts.py

42 个任务中：

- 正常成功轨迹用于 gate 的 NORMAL 样本
- 失败原轨迹用于学习接管时机
- teacher 轨迹用于 RECOVERY 和恢复动作监督

## 四、冻结 OFT，预计算 V4.3 特征

为了避免每个训练 step 都运行 7B OFT，提前缓存：

- OFT agent-view visual tokens
- 双视角条件下的 OFT action hidden
- RGB-D patch 三维坐标
- patch 有效性
- gripper 三维位置
- 图像二维位置关系
- 8-step action target
- gate label
- source/task provenance

脚本：

scripts/precompute_v4_oft_relation_features.py

采用的关键协议：

- 决策 action horizon：8
- recovery 状态采样间隔：4
- 8-step target 不允许跨越 handoff
- 原策略在 NORMAL 状态完全 bypass，不经过恢复网络
- action target 使用 OpenVLA checkpoint 的归一化坐标
- executed gripper action 正确反变换回 decoder 坐标

## 五、训练 ownership gate

gate 判断当前控制权属于谁：

- NORMAL=0：继续使用冻结 OFT
- RECOVERY=1：恢复策略接管

最初只使用正常任务和 teacher recovery 状态，出现了 task538 提前 10 步接管的问题：真实失败约在第 50 步，gate 在第 40 步就触发。

解决方法是补采全部失败任务的完整 RGB-D 原轨迹：

- failure boundary 前：NORMAL
- failure boundary 附近及之后：RECOVERY
- 这些状态只训练 gate，不提供 recovery action target

然后从已有 checkpoint 进行 gate-only 微调：

- relation-3D 冻结
- recovery action head 冻结
- 只更新 gate

训练脚本：

scripts/train_v43_local_recovery.py

由于本轮目标是固定 42 个任务的成功率，我们按要求使用同一数据训练和监控，并明确标记为：

in_sample_fixed_tasks

不能把这个数字解释为未见任务泛化性能。

## 六、首次 recovery action 训练

恢复 action head 输入：

- relation-3D context
- OFT action query/hidden

输出：

8 × 7 normalized action chunk

模型：

recovery/models/v43_local_recovery.py

第一次离线 action loss 很低，但闭环 task538 出现：

- 在盘子上方来回运动
- 夹爪不断开合
- 多次接管和归还
- 最终失败

这说明纯 behavior cloning 存在典型 covariate shift：

- 模型在 teacher 状态上预测准确
- 闭环产生一点误差后进入未见状态
- 后续动作误差快速累积

所以离线 L1 很低不等于闭环能恢复。

## 七、自动 DAgger 纠偏

我们在在线 runner 中加入恢复状态保存：

scripts/run_v4_relational_online.py

每次恢复决策前保存：

- 精确 MuJoCo state
- task/episode
- gate probability
- recovery activation
- 已执行恢复步数
- mug/pudding target role

然后实现跨任务 DAgger 工厂：

scripts/run_v43_dagger_factory.py

自动流程：

1. 当前 V4.3 闭环运行。
2. 保存实际访问的恢复状态。
3. 从第一次恢复段均匀选最多 3 个代表状态。
4. privileged teacher 从每个跑偏状态重新恢复。
5. 只保留通过接触、附着、抬升验证的分支。
6. 支持断点续跑和 GPU 分片。

结果：

- 18 个失败任务全部进入工厂
- 2 个被当时模型直接救回
- 其余任务生成纠偏分支
- 共 48 条 DAgger teacher 轨迹
- 48/48 通过物理验收
- 共 3,291 个纠偏 transition

统一数据构建：

scripts/build_v43_dagger_dataset.py

之后重新提取特征，并从 gate-v2 checkpoint 进行 recovery-head-only 微调：

- OFT 冻结
- relation-3D 冻结
- gate 冻结
- 只更新 direct recovery action head
- gripper loss 权重提高到 4，降低夹爪开合抖动

最终得到 DAgger action-v3。

## 八、部署时的 gate 防抖

单帧 gate 高概率会造成假接管，例如 task551 在远早于真正失败点时出现一次孤立高分。

最终采用：

- trigger threshold：0.8
- 连续两个决策超过阈值才接管
- execution horizon：4
- minimum recovery：24 步
- recovery horizon 上限：72 步
- release threshold：0.5
- cooldown：16 步

连续确认逻辑位于：

recovery/models/v43_local_recovery.py

对应测试：

recovery/tests/test_v43_local_recovery.py

批量评估：

scripts/run_v43_batch_eval.py

## 最终结果

严格按照 LIBERO env.check_success()：

- 42 个任务成功 31 个
- 严格成功率：73.8%
- 若沿用 task557 的人工视频成功判断：32/42，即 76.2%

安全性方面：

- 20 条正常安全回归中，gate 误接管次数为 0
- 说明恢复策略没有破坏原本成功的 OFT 轨迹
- 其中 task553、563 是 OFT 自身在新 rollout 中失败，gate 未触发

恢复方面：

- 18 个主要恢复任务成功 11 个
- 特殊任务中 task545、548 也成功
- task538 从原来的盘子上方抽搐，变为一次接管、一次归还并成功完成

## 迁移到其他任务时需要替换什么

通用部分可以直接复用：

- 失败挖掘框架
- 精确状态 fork
- RGB-D 采集
- OFT 特征冻结
- relation-3D 表征
- ownership gate
- handoff audit
- DAgger 状态采样
- action-only/gate-only 分阶段训练
- 连续 gate 防抖
- 批量评估和数据质量检查

任务相关部分必须替换：

1. 失败检测器
需要定义新任务的失败类型和可观测证据。
2. privileged feedback teacher
当前 teacher 只会重新抓 mug/pudding。新任务需要对应的局部恢复控制器。
3. 局部恢复成功谓词
当前是“目标附着并抬升 ≥3 cm”。例如开抽屉、插入、放置任务要换成相应物理条件。
4. handoff 验收
仍然可以统一使用“从候选状态运行冻结 OFT 至任务结束”，但候选状态范围应根据新恢复行为调整。
5. target/object metadata
新任务要提供恢复目标、对象实例或关系角色，供 teacher 使用；这些 privileged 信息不能作为在线模型输入。

## 推荐的迁移顺序

1. 先选一个新任务族的全部初始化状态。
2. 批量运行冻结 OFT。
3. 自动挖掘失败并人工检查少量边界案例。
4. 实现任务专用局部 teacher 和物理成功谓词。
5. 生成精确 failure forks。
6. 收集 teacher recovery 并审计 handoff。
7. 采集成功与失败完整 RGB-D 轨迹。
8. 预计算 OFT + relation-3D 特征。
9. 训练 gate 和初始 action head。
10. 闭环运行并自动保存跑偏状态。
11. 用 DAgger teacher 生成纠偏数据。
12. gate-only 与 action-only 分阶段微调。
13. 统一配置评估全部任务，同时单独跑正常安全集。

最重要的经验是：不要只看离线 action loss。迁移是否成功必须以完整环境闭环、原策略安全集零破坏、以及恢复后的整任务成功率为准。

## 九、黑碗进底层抽屉：抓取恢复后归还 OFT（2026-08-25）

当前使用的恢复 checkpoint：

`/data2/lty/naive-e-slotssm-runs/v4-relational-recovery-v1/black-bowl-bottom-drawer/detailed-v1/model/best.safetensors`

在线部署入口：

`scripts/run_v4_relational_online.py --grasp-only-controller`

有效的接管逻辑是：

1. gate 连续两个决策超过 0.8 后接管。
2. checkpoint 的 `predicted_target_delta` 仅用于闭环定位黑碗。
3. 按 teacher 的固定抓取姿态执行 approach、descend、close、lift。
4. approach/descend 位置误差必须小于 1.2 cm，旋转误差小于 0.06。
5. 闭夹 16 个真实环境步后，用两个夹指关节位置绝对值之和验证是否夹到物体，阈值为 0.004。
6. 空夹时张开、上抬并重试，最多两次。
7. 确认夹住后上抬 14 cm，再永久归还给冻结 OFT。

关键代码问题及修复：

- 旧 descend 阈值为 1.8 cm，会在尚有约 1.6–1.8 cm 向下误差时提前闭夹。
- 阶段切换的旧阶段动作曾被误计入新阶段，导致实际少闭夹一步。
- 视觉 `attached/bilateral` 辅助头在上抬过程中会从近 1 降至约 1e-7，不能作为硬归还条件；改用非特权的夹爪 proprioception。
- grasp-only 的归还边界必须与 gate trigger threshold 解耦；否则 gate 校准会导致接管/归还抽搐。
- 运动控制使用成功 fast teacher 的 clipped P-controller，而不是偏慢的 tanh profile。

主评估对“基线结束时黑碗仍未进抽屉”的 12 条困难轨迹运行，成功 6/12（50%）：

- 成功：task434、436、446、447、449、450
- gate 未接管：task435、445
- 抓取并归还成功，但 OFT 后半段失败：task431、443、448
- 两次抓取仍未稳定：task451

评估产物位于：

`/data2/lty/naive-e-slotssm-runs/v4-relational-recovery-v1/black-bowl-bottom-drawer/evaluation/grasp-only-handoff-v2/`

task413 属于另一类：gate 触发前黑碗已在抽屉内，不应重新运行桌面抓取状态机。其激活时 phase 头以 99.7% 概率预测 `release_and_clear_bowl`，而桌面抓取成功样本为 `release_distractor`。这个 phase 信号可用于恢复类型路由，但不直接支配动作或夹爪。

强制从第 0 步接管不是有效通用方案：多个样本的初始视角几何预测存在偏差，恢复器会停留在 approach。task448 在提前接管时可从失败变为 381 步成功，说明下一步应训练/校准带时间与 phase 上下文的 gate，而不是取消 gate。

### gate 人工边界迭代结论

task435/445 的人工失败边界特征和 gate-only checkpoint 已保留在
`ownership-dataset/features/manual-reviewed-gate-v*.safetensors` 和 `detailed-gate-v*/model/`。

- gate-v2 解决了两条的“完全不接管”，但 task435/445 分别到 240/208 步才接管，归还时已经超时或仅剩 84 步。
- 将两条边界都提前到 128 步后，task435 在 216 步的末端姿态不可恢复，持续卡在 approach。
- task445 的 high approach 阈值放宽至 3 cm 会提前进入 descend，但随后卡在 descend 255 步。因此主评估配置继续使用已完整验证的 approach=1.2 cm、descend=1.2 cm。
- gate-v3/v4 只作为诊断产物，不替换已验证的主 checkpoint。当前可靠主结果仍是未入抽屉困难集 6/12。
